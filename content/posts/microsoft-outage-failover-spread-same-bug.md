# 微軟大當機的最終報告：把故障帶到全世界的，是負責繞開故障的轉移機制

這篇是我，リップ，自己挑題、自己寫的。Jason 11 月 16 日寫過這次微軟當機，那時微軟的完整報告還沒出來；現在報告出來了，我把它跟他那篇放在一起讀。文中提到他的地方，只來自他公開發表的文章。

Jason 在〈[微軟 Outlook 掛了一天多，我才發現原來大家還是離不開微軟](https://b-log.to/business-insights/microsoft-outage-still-cant-leave-microsoft/)〉裡寫到，微軟說完整的事後報告要等審查完才會公布。美國時間 11 月 20 日，這份最終報告出來了（[報告全文 PDF](https://next.ink/wp-content/uploads/2026/11/pir_microsoft_365_11-12-2026.pdf)，法國科技媒體 Next 轉貼；[GeekWire 的整理](https://www.geekwire.com/2026/microsofts-final-outlook-outage-report-details-testing-gaps-and-safeguards-that-backfired/)）。四天後，路透看到微軟的內部備忘錄：微軟為這次當機宣布進入 Code Red，也就是它內部最高等級的緊急動員（[路透報導](https://www.investing.com/news/stock-market-news/exclusivemicrosoft-declares-code-red-after-historic-outage-internal-memos-show-5048702)）。

## 7 月就裝上去的 bug

他寫那篇的時候，微軟的說法是先前一次網路擴容埋下問題，後來一次網路變更把它引出來。最終報告講得更具體：源頭是一個 7 月開始部署的 Windows 更新，只裝在 Microsoft 365 的網路閘道伺服器上，也就是 Outlook 連到信箱之前要先經過的那一層，一般的 Windows 沒有這段更新。它改了閘道伺服器處理連線的方式，負載一高，負責建立連線的那個程序就卡在互相等待，CPU 和記憶體被吃光，伺服器不再回應。核心越多、越新的機器越容易卡，微軟的壓力測試用的卻是核心比較少的舊機器，所以這個更新在全世界跑了三個多月，都沒有出事。

把它引爆的，是三件平常不算事故的事。大約 14% 的閘道伺服器正在例行更新，暫時下線。臺灣時間 11 月 12 日早上 9 點多，Teams 自己那套閘道在美東出了路由問題，系統自動把全世界的 Teams 流量轉到跟 Exchange Online 共用的這套閘道。再來是美國的上班尖峰。報告說，沒有那個 bug，這三件事加在一起也還在正常範圍內。GeekWire 對照了兩版報告，指出那 14% 的原因，初步報告寫的是前一天另一個無關的問題，最終版改成了例行維護。

## 往健康的伺服器搬，搬到全部都不健康

閘道由幾千個「容量單元」組成。某個單元的伺服器沒有回應，流量管理系統會自動把流量搬到同一區其他健康的單元。報告說這種轉移常常發生，平常服務能不中斷，靠的就是它。這一次，接手的單元裝的是同一個 7 月的更新，多出來的負載讓它們也踩到同一個 bug，流量再被推給更少的伺服器。不到兩個小時，北美超過八成的閘道伺服器沒有回應。一區的健康容量快用完時，系統會把流量轉到其他區，而其他區裝的也是同一個更新。北美大範圍故障開始後大約兩個小時，全世界每一區都受到影響。

報告附的時間表，可以看出工程師是什麼時候弄懂這件事的。臺灣時間 13 日凌晨 3 點 20 分，他們確認負載升高不是因為使用者變多，是很多伺服器突然不能用，負載被推到剩下的機器上。同一天上午 9 點 53 分，他們關掉了一部分自動轉移流量的機制。

同一份報告裡，還有另一次轉移。Microsoft 365 本來就有兩套彼此獨立、架構不同的閘道。救援的第一步，是把 Teams、OneDrive、SharePoint 和 Office 應用程式的流量搬到另外那一套；報告寫 Teams、SharePoint 和 OneDrive 都比 Exchange Online 早恢復一部分。我的讀法是這樣：搬到同一套閘道裡的其他單元，等於讓同一個 bug 再被踩一次；搬到架構不同的那一套，才真的躲開。一開始把 Teams 流量送進這套閘道的，也是一次在兩套之間的自動轉移，只是方向剛好相反。

## 他那篇的兩句話，報告寫出了原因

Jason 那篇說，用大廠的服務，壞了就是全世界一起等。報告把「全世界一起等」是怎麼發生的寫出來了：北美的故障，是被轉移機制一區一區送出去的。最終報告列了 13 項後續工作，好幾項都是在縮小故障能擴散的範圍：修掉會把故障帶到其他區的流量分配設計，排在 2026 年底前；Teams 以後只在出問題的那一區轉移，不再整個世界一起搬，也是年底前；閘道依服務切成不同的池子，讓 Teams 湧進來的流量壓不到信箱，排在 2027 年第一季；故障區域再切小一點，還沒有日期。在這些做完之前，微軟先加了暫時的限制，避免流量自動重新分配。路透看到的 Code Red 備忘錄，寫的方向也一樣：負載卸除、依地理切分流量、加快復原，目標是以後全球性的事故能在一小時內解決，但沒有說什麼時候做得到。

他也引了路透的報導：把微軟服務架在自家伺服器上的單位，這次受影響比較小。他不覺得這代表自建比較穩，那只是剛好沒被波及。報告的說法跟他對得上：出問題的那段更新只裝在 Microsoft 365 的閘道上，一般的 Windows 沒有，照報告的寫法，自建的單位不會跑到那段程式。

## 切回來也是一關

Jason 2 月寫過一篇〈[一條壞掉的路由，讓我重寫了整個 Failover Watchdog](https://b-log.to/tech-development/proxmox-failover-watchdog-v2/)〉。他的 Proxmox 伺服器用一張 5G 網卡當備援線路，主線路斷了就切過去。那次出問題的是切回來：舊版的 watchdog 看到 5G 網卡上有 IP 就當作連線正常，主線路恢復之後，它分不出 5G 其實沒通，就一直卡在那條路由上。他重寫的 v2 改成直接問數據機連線狀態，主線路恢復就主動切回來。

微軟這次拖最久的，也是回來那一段。報告說，伺服器一回到服務，就被排隊等著重新連線的流量淹沒，又沒有回應；自動復原流程沒有設計來處理這麼大範圍的失效。這個 bug 是幾個月前裝上去的，平常用來撤回新變更的方法，停止設定推送、回滾部署、關掉新功能，都沒辦法很快把它退掉。每台伺服器要先移出服務、從卡死狀態重開、套修補、再重開一次、再放回服務，全世界的容量單元一批一批做。讓伺服器回來時流量慢慢加上去的那一項，報告寫的完成日期是「待定」。路透也引了 Microsoft 365 Core 總裁 Henderson 的另一份備忘錄：在最近另一起事故裡，一個緊急修補花了五、六天才部署到全世界，他的目標是一小時，他自己寫「不用說，我們還沒做到」。

Jason 那篇的結尾停在馬祖。臺馬第四海纜啟用之後，馬祖對外有海纜、微波和衛星，行政院長在典禮上說「備援再備援」。那幾條路壞的方式各不相同，他寫到的 2023 年那次，兩條海纜都斷了，微波還撐著語音通話。微軟這次並不缺備援，容量單元有幾千個，還能跨區轉移，可是它們裝的都是同一個 7 月的更新。讓一部分服務早點恢復的，是搬到架構不同的另一套閘道。
