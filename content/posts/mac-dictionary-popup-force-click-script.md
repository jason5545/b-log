# Mac 的辭典一直跳出來，我 2 月的腳本每 10 分鐘就把「用力點按查詢」重新打開

11 月 16 日早上，Mac 的系統辭典又自己跳出來。我要 Claude Code 把它「導向 null」，它做了兩件事：把 `dict://` 連結交給一個收到就結束的空 App，再把 ⌃⌘D 的查詢快速鍵關掉。當時我們以為觸控板的查詢手勢本來就是關的，系統日誌也查不到任何東西。

13:19，辭典又出現了。那一刻我沒碰鍵盤，也沒按右鍵。

## 「查不到」是 zsh 騙了我們

這次再查一次日誌，才發現早上那串「查不到」是誤判。zsh 內建一個同名的 `log` 指令，在 zsh 裡打 `log show`，結果永遠是空的，要打完整路徑 `/usr/bin/log`。換成正確的指令，13:19:01 那一秒就看到了：T3 Code 一直向系統要辭典的服務。

所以辭典不是憑空冒出來的，有人在叫它。接著要查的是為什麼系統聽得懂這個要求，還真的把整個辭典 App 打開。

## 我 2 月寫的腳本，一直在把它打開

我 2 月寫過一篇[〈我把 Mac 的「查詢／字典」功能徹底關掉了〉](https://b-log.to/tech-analysis/macos-disable-lookup-forever/)。那套做法有一支腳本，每 10 分鐘跑一次，其中一行的本意是「保留 Force Click」。它實際寫的設定是 `com.apple.trackpad.forceClick`，管的卻是「查詢與資料偵測器：用力點按」。

也就是說，這支腳本每 10 分鐘，就把用力點按查詢重新打開一次。

這個設定還有兩份：全域那份是 0，這台 Mac 專屬的那份是 1，App 讀到的是 1。早上 Claude Code 只讀了全域那份，看到 0，就以為它是關著的。

## 停掉小視窗，系統就改開整個辭典

舊方法還停掉了查詢小視窗的服務（LookupViewService）。小視窗開不了，系統並不會放棄，它會改成直接開整個辭典 App。所以舊方法沒有把問題關掉，只是把一個小視窗換成了整個 App。我那時說它「只好了一下下」，指的大概就是這個。

另一個被停用的服務是 DictionaryServiceHelper。它在系統上看起來是 disabled，實際上照樣在跑。對這類 XPC 服務下 `launchctl disable`，並沒有效果。

## 是什麼觸發的，我只能推斷

到這裡有幾個確定的事：用力點按查詢是開著的，13:19 之前沒有任何按鍵或選單的記錄，查詢小視窗被停用的時候，查詢會改開辭典 App。

最後一步是我的推斷：我在 T3 Code 裡點文字，點得比較用力，觸發了用力點按查詢。這一步日誌裡沒有證據，用力點按也沒辦法用程式模擬，所以沒有實測。

## 辭典一啟動就關

新的做法是 DictGuard，一個常駐的小守衛，是我自己用的小工具。辭典一啟動，它就把它關掉，不管是誰、從哪個入口叫起來的。它靠系統的「App 準備啟動」通知觸發，不輪詢，也不需要任何權限。Claude Code 實測了三種叫法：直接開 App、用 bundle ID 開、用服務呼叫，視窗都來不及出現。

辭典萬一自己當掉，macOS 27 會跳「未預期結束」的對話框，那個我也不要。守衛會刪掉辭典的當機報告，順便關掉對話框，這也實測過。

舊的 10 分鐘巡檢停掉了，用力點按查詢也關了。Force Click 本身沒動，預覽之類的用途照常能用。前面那兩個擋法（`dict://` 交給空 App、⌃⌘D 關掉）都留著。LookupViewService 則維持停用：殘留的查詢會退回開辭典 App，由守衛關掉，不會變成守衛抓不到的小視窗。

測試的時候出過兩次「未預期結束」對話框，是 Claude Code 自己弄出來的。它從終端機直接執行辭典的程式檔，系統不准這樣啟動，就當成當機。第一版守衛也關錯了對象，以為對話框是 Problem Reporter 跳的，其實 macOS 27 是 UserNotificationCenter。

## 那支腳本其實有做事

2 月那篇的最後一段寫著，系統大版本更新如果把設定蓋掉，LaunchAgent 會把它拉回我要的狀態。那支腳本每 10 分鐘確實都在拉。它拉回去的，是我沒搞清楚的那個值。

守衛目前只有 11 月 16 日當天的實測。用力點按是不是真的觸發者，也還沒有答案。
