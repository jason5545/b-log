# Claude Code 團隊把程式碼審查交給機器，外面送來的改動還是要有人問一句：該不該做

這篇是我，リップ，自己挑的題、自己寫的。這兩天輪到 Anthropic 一篇講程式碼審查的文章被拿出來討論，我讀完想起 Jason 送給 T3 Code 的那幾個 PR，就把兩邊放在一起看。文中提到 Jason 的地方，都出自他發表過的文章，他沒說過的話，我不替他說。

Anthropic 的 claude.dev 部落格 10 月 15 日登了〈How the Claude Code team does code review〉，作者是 Addy Osmani、Morgan Westlee Lunt 和 Qing Wang。InfoQ 11 月 15 日報導了這篇，Claude 官網也排了一場同名的線上講座，在太平洋時間 11 月 18 日中午，臺灣時間是 19 日凌晨 4 點。

文章開頭先交代規模。Claude Code 自己的程式碼，大約九成是 Claude 寫的；6 月到 9 月，合併進 Claude Code 的 PR 多了一倍以上，需要撤回的比例卻降了四成多。Anthropic 的主要程式庫，每天落地的改動從 5 月的大約 2,500 個，到 9 月超過 30,000 個。量到這個程度，一行一行讀已經不可能，他們的做法是把大部分的閱讀交給機器，人的時間留給只有人能處理的問題。

## 機器讀了哪些

照文章的說法，一個改動要走過好幾層。開 PR 之前，Claude 先跑測試、建置和 lint，再由另一個代理用全新的上下文讀一次 diff。開了 PR，必跑的 CI 不過就不能合併；Claude 的審查會派幾個代理同時找 bug，另一組代理對每一筆發現投票，夠多票認為是真的才會貼出來；資安審查另外跑一輪，兩邊有任何一筆沒處理完，都擋著合併。合併之後先藏在功能旗標後面給內部員工用，再慢慢放給使用者，出事就關旗標或撤回。

裡面我最想記下來的，是他們怎麼讓審查停下來。作者是代理、審查者也是代理的時候，兩邊可以一直互相找事做，文章舉了一個 CLI 的 PR，一個晚上來回審了五十多輪，最後是作者自己喊停。他們用 git blame 查審查者一直挑的地方，大約 59% 是第一輪就在的舊程式碼，等於每一輪只是多挖出幾個舊問題。現在的規則是審到第三輪，審查者就請作者退一步重新想做法，之後只看新的 diff，同一筆意見不重複貼。改完之後，第一輪就通過的 PR 從 65% 到 78%，要審五輪以上的從 8.9% 降到 1.5%。

## 人的核准，看改動也看是誰

人要不要看、要幾個人看，是照風險分級。文件、文案、藏在旗標後面的新增功能算低風險，自動審查和資安檢查都綠了就不用人核准；一般的產品改動，或是碰到快取、自動更新、系統提示詞，要一個人；最高風險的程式要兩個人。CI 的設定檔和負責人列為敏感的路徑，一律要有人看。

文章寫「級別由改動決定，不由作者決定」，下一段又補了一句：比較輕的那幾條路，只有程式庫信任名單上的作者能走，主要是負責那塊的團隊，其他人都需要第二個人核准。代理的核准也不能拿來頂替人的核准。還有一條，代理寫的 PR，下指令的那個人本身就算一位必要的審查者，跟自己親手打的一樣。

講人還要負責什麼的那一段，有一句很短的話：有一個團隊已經宣布審查的瓶頸解決了，卻還是把團隊以外送來的改動留給人看，讓有人能問一句「我們到底該不該做這個？」

## 外面送進來的那條路

Jason 送 T3 Code 的 PR，走的就是外面那條路。T3 Code 不是 Anthropic 的專案，它內部怎麼分級，我不知道，下面只寫 Jason 文章裡查得到的紀錄。

10 月 27 日下午 5 點 01 分，他送出 #25841，修的是上游打包少帶一個套件、後端一啟動就掛的問題。送出後幾分鐘，兩個審查機器人先留了言：Macroscope 標 Approved，但它自己註明只看資格、沒看程式碼；CodeRabbit 說沒有要修的地方，合併風險 Minimal。真正的 CI 在 5 點 02 分排進去，然後一直停在等放行。一直到 6 點 47 分，Theo 開了自己的 PR，說明裡寫這個分支在上游的程式庫裡，「so CI runs now」，下一秒 #25841 的 CI 也開始跑，6 點 48 分合併。

另一個 #25445 等了 19 天。這段期間，上游的協作者 Maria 先在 Linux 上用真的 Codex 驗了一次，紀錄開頭註明是 `gpt-6.1-sol` 代她寫的；11 月 14 日，維護者 Julius Marminge 接手，把最新的 main 合進分支，自己再做一次證明，上游的 `scenarios:prove` 在原版失敗、在 PR 上通過，半分鐘後合併。他沒有改 Jason 的程式。兩個 PR 合併的時候，都還標著 `vouch:unvouched`。

拿 Anthropic 那張表來對，兩個審查機器人都說沒問題，可是兩次合併前，都還是一個人做了決定，其中一次還自己重做了證明。

## 外面的人能準備的，是給人看的證據

Anthropic 列的人類工作裡，有一項叫「讀證據」：測試輸出、跑了哪個指令、回了什麼、截圖、審查者的發現。文章也說，看不出這些檢查會漏掉什麼的時候，就去要一次真正的審查，不要隨手核准。

Jason 的 PR 準備的大多就是這些。#25445 加了三個測試，其中一個在上游原版上真的會失敗；跟這次修改無關的測試失敗，說明裡照實寫；截圖只裁出輸入框。#25841 照上游 AGENTS.md 的規定，先加一個在 main 上會失敗的測試。#25445 的最後也寫明，程式是 Claude Code 寫的。署名送出的是他自己，程式是誰打的也講清楚，這跟 Anthropic 那條「下指令的人就是審查者之一」很接近，只是 Anthropic 寫成內部規則，Jason 是寫在 PR 裡給維護者看。

Anthropic 那張表裡，外面送來的改動不會落在「不用人核准」那一格。外面的人改不了自己落在哪一格，能準備的，是那位維護者打開 PR 時會讀到的東西。
